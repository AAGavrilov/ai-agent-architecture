## 4. Architecture Overview

Задача — продолжение установленного паттерна вендоринга, референс — `.agents/skills/grilling/SKILL.md`: harness-нейтральные редактируемые копии в `.agents/skills/`, адаптируется только вывод под контракт проекта, upstream-дисциплина сохраняется. Новых механизмов не вводится: процесс установки определён адаптером §4, ограничение роли — `AGENTS.md` §9, конвенция идентификаторов — `БЛОК 0.1` промтов. Изменения декларативные: два новых файла-скилла, три правки состояния (адаптер, `Memory.md`, `README.md`).

## 5. Architecture Decisions

- **DEC-001** — `grill-me` не вендорится; в адаптере §2 получает статус «покрыт вендоренным `grilling`». Рационал: это user-invoked обёртка того же примитива; trigger-фразы уже включены в описание вендоренной копии `grilling`; отдельный файл — дубликат механизма (`AGENTS.md` §6). Решение по `Q-002`.
- **DEC-002** — Находки `research` переносятся в предметные секции `PROJECT_SPEC` (выбор стека, ограничения, зависимости) с цитированием первоисточников; отдельные закоммиченные файлы не создаются. Черновики, если нужны, — некоммитимые рабочие файлы вне `docs/agent/`. Рационал: контракт «артефакт итерации один». Решение по `Q-003`.
- **DEC-003** — `to-questionnaire` эмитит `Q-NNN` сразу: анкета и есть список открытых вопросов; идентификаторы по `БЛОК 0.1` (три цифры, продолжение сквозной проектной нумерации с последнего существующего `Q-`). Рационал: устраняет ручной перенос и рассинхрон ID. Решение по `Q-004`.
- **DEC-004** — Механика `research` формулируется harness-нейтрально: «используй доступные в среде средства поиска (web, чтение репозитория, команды); находки — с цитированием первоисточника». Рационал: выбор harness отложен (ASM-002) и не должен влиять на содержание скилла. Решение по `Q-005`.

## 13. Error Model

| Ситуация | Обработка |
| --- | --- |
| Upstream недоступен при вендоринге | Кодер не реконструирует текст по описанию: фиксируется `BLK-` с последним работающим коммитом (`ORCHESTRATOR.md`, раздел 5) |

## 15. Edge Cases

- Дерево решений пусто (спорить не о чем): `to-questionnaire` фиксирует «открытых вопросов нет» явно, не генерирует пустышки.
- Среда без сетевого доступа: `research` деградирует до локальных фактов (репозиторий, команды) с явной пометкой ограничения; недоступное — `Q-`/`ASM-`, не молчаливое умолчание.
- Дрейф upstream после вендоринга — ожидаемое состояние, а не ошибка (адаптер §4, правило 3).

Секция добавлена патчем формализации workflow (2026-09-27): фиксирует контракт state machine каркаса. Каноническое определение transitions — `.agents/STATE_MACHINE.md`; runtime state — `docs/agent/STATE.md`; исполнение — `.agents/ORCHESTRATOR.md`.

- **REQ-HARNESS-001** — State machine существует как отдельный нормативный документ (`.agents/STATE_MACHINE.md`).
- **REQ-HARNESS-002** — Каждое состояние имеет однозначные допустимые transitions.
- **REQ-HARNESS-003** — Runtime state хранится только в `docs/agent/STATE.md`.
- **REQ-HARNESS-004** — `Memory.md` не хранит volatile workflow state.
- **REQ-HARNESS-005** — Architecture, Implementation и Review имеют однозначные commit contracts.
- **REQ-HARNESS-006** — Implementation baseline определяется только через implementation commits.
- **REQ-HARNESS-007** — Review всегда имеет Review commit.
- **REQ-HARNESS-008** — `Q-*` без safe `ASM-*` переводит workflow в `WAITING_HUMAN`.
- **REQ-HARNESS-009** — `REJECTED` применяется только к architecture-level failure.
- **REQ-HARNESS-010** — `POTENTIAL` не является severity.
- **REQ-HARNESS-011** — Block 0 автоматически проверяется на идентичность.
- **REQ-HARNESS-012** — Illegal state transitions обнаруживаются автоматически.
- **REQ-HARNESS-013** — Нельзя перейти в `REVIEW_PENDING` без valid Implementation commit.
- **REQ-HARNESS-014** — Нельзя перейти в `COMPLETED` без valid Review verdict.
- **REQ-HARNESS-015** — Iteration limits enforced deterministically.
- **REQ-HARNESS-016** — NO_PROGRESS limit enforced deterministically.
- **REQ-HARNESS-017** — `STATE.md` содержит evidence для текущего state.
