# Оркестратор — протокол итерации

Проект состоит из трёх ролей: Архитектор / Кодер / Ревьювер.

Три агента обмениваются не текстом в чате, а файлами артефактов с контрактами: Архитектор формирует `PROJECT_SPEC`, Кодер — `IMPLEMENTATION`, Ревьювер — `REVIEW_REPORT`.

Каждый артефакт — файл в репозитории (`docs/agent/`), код — в файлах репозитория, общение идёт через чтение файлов и git, а не через пересказ в памяти. Поэтому в каждом промте присутствует `БЛОК 0. ОБЩИЙ КОНТРАКТ` — он идентичен во всех трёх промтах намеренно, потому что каждый промт копируется отдельно и должен быть самодостаточным. При правке общего блока менять его во всех трёх местах одновременно.

Промпты ролей вынесены в отдельные файлы; этот файл — протокол запуска:

- `.agents/prompts/01-analysis.md` — Архитектор → `docs/agent/PROJECT_SPEC.md`
- `.agents/prompts/02-implementation.md` — Кодер → `docs/agent/IMPLEMENTATION.md`
- `.agents/prompts/03-review.md` — Ревьювер → `docs/agent/REVIEW_REPORT.md`
- `.agents/ORCHESTRATOR.md` (этот файл) — протокол итерации

## 4. Оркестратор — протокол итерации

Этот блок — не системный промт агента. Его выполняет человек или primary-агент, который запускает три роли по очереди и передаёт им файлы из `docs/agent/`.

### 4.1 ПАРАМЕТРЫ ПРОТОКОЛА

| Параметр | По умолчанию | Как меняется |
| --- | --- | --- |
| Лимит итераций | 3 | правкой этого блока до запуска |
| Базовая ветка | текущая | аргументом запуска |
| Обязательные проверки Кодера | build, typecheck, lint, tests | берутся из репозитория |
| Обязательные проверки Ревьювера | те же плюс аудит по диффу | — |

### 4.2 ПОРЯДОК ЗАПУСКА

1. **Итерация 1, Архитектор.** Вход: требования пользователя, код репозитория. Выход: `docs/agent/PROJECT_SPEC.md`, коммит.
2. **Итерация 1, Кодер.** Вход: `PROJECT_SPEC.md`. Выход: код, `IMPLEMENTATION.md`, коммит `Iteration 1`.
3. **Итерация 1, Ревьювер.** Вход: `PROJECT_SPEC.md`, `IMPLEMENTATION.md`, код, дельта коммита. Выход: `REVIEW_REPORT.md`, коммит.
4. **Маршрутизация по verdict** — см. 4.4.
5. **Итерация N+1, Кодер.** Вход: тот же `PROJECT_SPEC.md` плюс `REVIEW_REPORT.md`. Выход: коммит `Iteration N+1`.

Разделение ролей жёсткое: Ревьювер не правит код, Кодер не переписывает архитектуру, Архитектор не трогает код. Нарушение этого разделения — дефект процесса, а не замечание по коду.

Superpowers (см. `.agents/adapters/superpowers.md`) — execution-layer Кодера. Он не участвует в дизайне (это роль Архитектора) и не заменяет независимого Ревьювера. В сессиях Архитектора и Ревьювера bootstrap Superpowers (`using-superpowers`) подавляется; в сессии Кодера активен с ограниченным списком скиллов.

### 4.3 С ЧЕГО НАЧИНАЕТСЯ СЕССИЯ

| Роль | Обязательно прочитать до первой строки работы |
| --- | --- |
| Архитектор | требования пользователя, `AGENTS.md`, `Memory.md`, код репозитория |
| Кодер | `AGENTS.md`, `Memory.md`, `docs/agent/PROJECT_SPEC.md`; при N > 1 — `docs/agent/REVIEW_REPORT.md` и предыдущий `docs/agent/IMPLEMENTATION.md` |
| Ревьювер | `AGENTS.md`, `docs/agent/PROJECT_SPEC.md`, `docs/agent/IMPLEMENTATION.md`, код, дельта итерации |

`Memory.md` — долговременная память проекта: контекст, а не контракт. Для вердикта Ревьювера она доказательством не является.

Сессия, начатая без этих файлов, неполна: её результат нельзя адресно проверить.

### 4.4 МАРШРУТИЗАЦИЯ ПО VERDICT

| Verdict | Действие |
| --- | --- |
| `APPROVED` | цикл завершён, артефакты остаются в репозитории |
| `APPROVED_WITH_CHANGES` | цикл завершён, `LOW` остаются как есть |
| `CHANGES_REQUIRED` | Кодер, итерация N+1 |
| `REJECTED` | возврат Архитектору, см. 4.5 |

### 4.5 ЭСКАЛАЦИЯ

`BLK-001` — Кодер не может реализовать контракт:

1. Кодер останавливает итерацию, оставляет `IMPLEMENTATION.md` с блокером и последним работающим коммитом.
2. Архитектор пересобирает `PROJECT_SPEC.md` **инкрементально**: добавляет или уточняет `DEC-`, помечая затронутые `REQ-`.
3. Кодер начинает итерацию N+1 с обновлённым `PROJECT_SPEC.md`. Уже сделанная работа не откатывается.

`CONFLICT-001` — дефект в самой архитектуре: маршрут тот же, но Архитектор ревизует конкретное `DEC-` и фиксирует, почему прежнее решение не работает.

`Q-001` — недостаточно данных: единственный повод прерваться и спросить человека. Пока ответа нет, Кодер применяет временное допущение из `PROJECT_SPEC` и помечает его `ASM-`, а не идёт дальше по своему усмотрению.

### 4.6 ОСТАНОВКА

Цикл считается успешно завершённым только если последний `REVIEW_REPORT` имеет `APPROVED` или `APPROVED_WITH_CHANGES` и одновременно:

* нет `BLOCKER`;
* нет `HIGH`;
* нет `MEDIUM`;
* нет `FAIL` по критическим `REQ-`;
* нет `NOT_TESTED` по критическим `REQ-`;
* нет открытых критических `REV-`;
* нет блокирующих `CONFLICT-`;
* нет открытых критических `BLK-`;
* нет открытых критических `BIMP-`;
* обязательные проверки выполнены или доказанно `NOT_APPLICABLE`.

`APPROVED_WITH_CHANGES` допускает только некритичные `LOW`.

Цикл останавливается досрочно при исчерпании лимита итераций, нерешаемом архитектурном конфликте, отсутствии критически важной информации без безопасного `ASM-`, либо если один и тот же критический `REV-` остаётся открытым третью implementation-итерацию.

При досрочной остановке указываются открытые `REV-`, `BLK-`, `BIMP-`, `CONFLICT-`, проблемные `REQ-`, последний `VERDICT` и причина остановки.

### 4.7 ЧТО СЧИТАЕТСЯ ПРОГРЕССОМ ИТЕРАЦИИ

Итерация считается прогрессивной, если выполнено хотя бы одно:

1. закрыт `REV-`;
2. уменьшено число `FAIL` или `NOT_TESTED` по `REQ-`;
3. устранён `BLK-`;
4. устранён `BIMP-`;
5. подтверждён ранее непроверенный архитектурный контракт;
6. устранён регресс;
7. требование перешло по цепочке `OPEN → IMPLEMENTED → VERIFIED`.

Само изменение кода без изменения проверяемого состояния не считается прогрессом.

Изменение только `IMPLEMENTATION.md` не считается прогрессом.

Если количество изменений выросло, но проверяемое состояние не улучшилось, итерация считается `NO_PROGRESS`.

### ФИНАЛЬНОЕ ПРАВИЛО

Не считай текст артефакта доказательством сам по себе.

Приоритет источников истины:

1. фактическое состояние файлов репозитория;
2. фактический результат команды или теста;
3. Git history и implementation diff;
4. `PROJECT_SPEC`;
5. `IMPLEMENTATION`;
6. `REVIEW_REPORT`;
7. память агента или предположение.

Если источники противоречат друг другу, более высокий источник имеет приоритет,
а противоречие должно быть явно зафиксировано.

Никогда не превращай отсутствие доказательства в доказательство успеха.
