# Оркестратор — протокол итерации

Проект состоит из трёх ролей: Архитектор / Кодер / Ревьювер.

Три агента обмениваются не текстом в чате, а файлами артефактов с контрактами: Архитектор формирует `PROJECT_SPEC`, Кодер — `IMPLEMENTATION`, Ревьювер — `REVIEW_REPORT`.

Каждый артефакт — файл в репозитории (`docs/agent/`), код — в файлах репозитория, общение идёт через чтение файлов и git, а не через пересказ в памяти. Поэтому в каждом промте присутствует `БЛОК 0. ОБЩИЙ КОНТРАКТ` — он идентичен во всех трёх промтах намеренно, потому что каждый промт копируется отдельно и должен быть самодостаточным. При правке общего блока менять его во всех трёх местах одновременно; битовая идентичность проверяется скриптом `tests/harness/check-block0.sh`.

Промпты ролей вынесены в отдельные файлы; этот файл — протокол запуска:

- `.agents/prompts/01-analysis.md` — Архитектор → `docs/agent/PROJECT_SPEC.md`
- `.agents/prompts/02-implementation.md` — Кодер → `docs/agent/IMPLEMENTATION.md`
- `.agents/prompts/03-review.md` — Ревьювер → `docs/agent/REVIEW_REPORT.md`
- `.agents/STATE_MACHINE.md` — каноническое определение workflow state machine
- `.agents/ORCHESTRATOR.md` (этот файл) — протокол итерации

## Canonical Workflow Protocol

Каноническое определение workflow state machine находится в:

.agents/STATE_MACHINE.md

## Протокол итерации

Этот блок — не системный промт агента. Его выполняет человек или primary-агент, который запускает три роли по очереди и передаёт им файлы из `docs/agent/`.

### 1. ПАРАМЕТРЫ ПРОТОКОЛА

| Параметр | По умолчанию | Как меняется |
| --- | --- | --- |
| Базовая ветка | текущая | аргументом запуска |
| Обязательные проверки Кодера | build, typecheck, lint, tests | берутся из репозитория |
| Обязательные проверки Ревьювера | те же плюс аудит по диффу | — |

Лимиты итераций вынесены в раздел «LIMITS»: вместо одного неоднозначного «лимита итераций» используются независимые счётчики с отдельными пределами.

### 2. EXECUTION LOOP

1. Прочитай `docs/agent/STATE.md`.
2. Проверь, что запрошенная роль разрешена в текущем состоянии (STATE GATE промта роли).
3. Выполни промпт роли.
4. Проверь произведённый артефакт.
5. Проверь обязательный Git commit.
6. Обнови `docs/agent/STATE.md`.
7. Примени transition по verdict.
8. Запусти `bash tests/harness/check-all.sh` — workflow продолжается только при exit code 0.
9. Остановись при нелегальном transition, blocking Q-*, достижении лимита или unrecoverable-ошибке.

Форматы всех трёх типов артефактных коммитов и правило дельты определены в GIT-ПРОТОКОЛЕ промта Кодера (`.agents/prompts/02-implementation.md`, §15). Правки каркаса вне итераций коммитируются обычными conventional-коммитами и не являются implementation baseline.

Разделение ролей жёсткое: Ревьювер не правит код, Кодер не переписывает архитектуру, Архитектор не трогает код. Нарушение этого разделения — дефект процесса, а не замечание по коду.

Superpowers (см. `.agents/adapters/superpowers.md`) — execution-layer Кодера. Он не участвует в дизайне (это роль Архитектора) и не заменяет независимого Ревьювера. В сессиях Архитектора и Ревьювера скиллы Superpowers игнорируются, а bootstrap при возможности технически подавляется (универсальное правило — `AGENTS.md`, §9); в сессии Кодера активен с ограниченным списком скиллов.

Набор mattpocock/skills (см. `.agents/adapters/mattpocock-skills.md`) — execution-layer Архитектора: дисциплина выяснения требований (структурированное интервью, анкеты, исследование с первоисточниками). Он не принимает проектных решений вместо Архитектора; в сессиях Кодера и Ревьювера его скиллы игнорируются (то же универсальное правило). Ревьювер работает без execution-layer намеренно: независимость ревью — его ценность.

### 3. С ЧЕГО НАЧИНАЕТСЯ СЕССИЯ

| Роль | Обязательно прочитать до первой строки работы |
| --- | --- |
| Архитектор | требования пользователя, `AGENTS.md`, `Memory.md`, `docs/agent/STATE.md`, код репозитория |
| Кодер | `AGENTS.md`, `Memory.md`, `docs/agent/STATE.md`, `docs/agent/PROJECT_SPEC.md`; при N > 1 — `docs/agent/REVIEW_REPORT.md` и предыдущий `docs/agent/IMPLEMENTATION.md` |
| Ревьювер | `AGENTS.md`, `docs/agent/STATE.md`, `docs/agent/PROJECT_SPEC.md`, `docs/agent/IMPLEMENTATION.md`, код, дельта итерации |

`Memory.md` — долговременная память проекта: контекст, а не контракт. Для вердикта Ревьювера она доказательством не является. Runtime workflow state хранится только в `docs/agent/STATE.md`.

Сессия, начатая без этих файлов, неполна: её результат нельзя адресно проверить.

### 4. VERDICT SEMANTICS

Каноническая transition matrix определена только в `.agents/STATE_MACHINE.md`; здесь — семантика вердиктов и их маршрутизация.

#### APPROVED

Текущая реализация удовлетворяет применимому архитектурному контракту и требуемые доказательства верификации присутствуют.

Transition:

    REVIEW_READY -> COMPLETED

#### APPROVED_WITH_CHANGES

Реализация удовлетворяет обязательному контракту, но остаются некритичные (non-blocking) follow-up пункты.

Transition:

    REVIEW_READY -> COMPLETED

#### CHANGES_REQUIRED

Архитектура принята, но реализация требует дополнительной работы.

Transition:

    REVIEW_READY -> IMPLEMENTATION_PENDING

#### REJECTED

Реализация не может быть исправлена без пересмотра архитектурного контракта, либо существует обязательный архитектурный конфликт.

Transition:

    REVIEW_READY -> ARCHITECTURE_PENDING

### 5. REJECTED CONSTRAINT

`REJECTED` MUST NOT использоваться как усиленная форма `CHANGES_REQUIRED`.

`REJECTED` допустим только если существует хотя бы одно из:

- `CONFLICT-*`, затрагивающий обязательный архитектурный контракт;
- невыполнимое обязательное требование;
- архитектурное противоречие;
- архитектурное решение, которое должно быть пересмотрено до продолжения реализации.

Баги реализации — только `CHANGES_REQUIRED`. Недостающая реализация — только `CHANGES_REQUIRED`. Неполные тесты — только `CHANGES_REQUIRED`.

Вердикт `REJECTED` MUST идентифицировать затронутые `DEC-*`, `REQ-*` или `CONFLICT-*`.

### 6. ЭСКАЛАЦИЯ

`BLK-001` — Кодер не может реализовать контракт:

1. Кодер останавливает итерацию, оставляет `IMPLEMENTATION.md` с блокером и последним работающим коммитом.
2. Архитектор пересобирает `PROJECT_SPEC.md` **инкрементально**: добавляет или уточняет `DEC-`, помечая затронутые `REQ-`.
3. Кодер начинает итерацию N+1 с обновлённым `PROJECT_SPEC.md`. Уже сделанная работа не откатывается.

`CONFLICT-001` — дефект в самой архитектуре: маршрут тот же, но Архитектор ревизует конкретное `DEC-` и фиксирует, почему прежнее решение не работает.

Blocking `Q-*` обрабатываются по разделу «Q-* AND ASM-* PROTOCOL» (ниже).

### 7. Q-* AND ASM-* PROTOCOL

`Q-*` — блокирующая неизвестность.

Если недостающая информация влияет на обязательное архитектурное или реализационное решение и не существует безопасного временного допущения:

    current state -> WAITING_HUMAN

`ASM-*` — неблокирующее временное допущение.

`ASM-*` допустим только когда:

1. допущение явно зафиксировано;
2. допущение имеет ограниченный (bounded) эффект;
3. допущение не нарушает текущий архитектурный контракт;
4. допущение можно заменить без инвалидизации несвязанной работы;
5. неопределённость на самом деле не блокирует.

Агент MUST NOT молча понижать `Q-*` до `ASM-*`.

`Q-*` считается resolved, когда зафиксирован одобренный `ASM-*` или получен ответ человека; до этого blocking `Q-*` остаётся unresolved и удерживает workflow в `WAITING_HUMAN`.

### 8. LIMITS

Workflow использует независимые счётчики (см. `docs/agent/STATE.md`):

- `architecture_revision`
- `implementation_iteration`
- `review_iteration`
- `no_progress_count`

Сконфигурированные пределы:

- максимум implementation-итераций: 3
- максимум architecture-ревизий: 3
- максимум последовательных NO_PROGRESS: 2

Нарушение лимита переводит workflow в `HALTED` (см. раздел «ОСТАНОВКА И HALTED»).

### 9. ОСТАНОВКА И HALTED

Цикл считается успешно завершённым (transition в `COMPLETED`) только если последний `REVIEW_REPORT` имеет `APPROVED` или `APPROVED_WITH_CHANGES` и одновременно:

* нет `BLOCKER`;
* нет `HIGH`;
* нет `MEDIUM`;
* нет `FAIL` по критическим `REQ-`;
* нет `NOT_TESTED` по критическим `REQ-`;
* нет открытых критических `REV-`;
* нет блокирующих `CONFLICT-`;
* нет открытых критических `BLK-`;
* нет открытых критических `BIMP-`;
* обязательные проверки выполнены или доказанно `NOT_APPLICABLE`.

`APPROVED_WITH_CHANGES` допускает только некритичные `LOW`.

Досрочная остановка оформляется как переход в `HALTED` с обязательной причиной:

* исчерпание лимита implementation-итераций → `ITERATION_LIMIT`;
* исчерпание лимита architecture-ревизий → `ARCHITECTURE_REVISION_LIMIT`;
* превышение числа последовательных `NO_PROGRESS` → `NO_PROGRESS`;
* нерешаемый без человека blocking `Q-*` → `WAITING_HUMAN`, а при невозможности продолжить — `HALTED` с причиной `MISSING_ARTIFACT`/`CONTRACT_VIOLATION`/`UNRECOVERABLE_ERROR`.

`HALTED` — terminal state: автоматический переход из него запрещён, возобновление — только новым explicit workflow start.

При досрочной остановке указываются открытые `REV-`, `BLK-`, `BIMP-`, `CONFLICT-`, проблемные `REQ-`, последний `VERDICT` и причина остановки.

### 10. NO_PROGRESS

Ревью фиксирует `NO_PROGRESS`, когда не устанавливает никакого содержательного улучшения состояния.

Содержательный прогресс включает хотя бы одно из:

- ранее открытый `REV-*` закрыт;
- ранее открытый `REQ-*` реализован;
- ранее открытый `REQ-*` получил доказательство верификации;
- `BLK-*` закрыт;
- `BIMP-*` закрыт;
- явно идентифицированный регресс исправлен;
- нерешённый контрактный вопрос решён;
- состояние реализации изменилось `OPEN → IMPLEMENTED`;
- состояние реализации изменилось `IMPLEMENTED → VERIFIED`.

Само изменение кода без изменения проверяемого состояния прогрессом не считается. Изменение только `IMPLEMENTATION.md` прогрессом не считается.

Последовательные `NO_PROGRESS` инкрементируют `no_progress_count`. При

    no_progress_count >= max_consecutive_no_progress

workflow переходит в

    HALTED / NO_PROGRESS

### 11. STATE COMMIT SEMANTICS

Обновление `docs/agent/STATE.md` — двухфазный процесс, чтобы STATE.md никогда не ссылался на несуществующий коммит.

Phase A — artifact commit. Сначала создаётся содержательный коммит (`Architecture N:` / `Iteration N:` / `Review N:`). Только после него SHA известен.

Phase B — state commit. Затем обновляется `docs/agent/STATE.md` и создаётся framework/state commit:

```text
State N: <transition description>
```

Пример:

```text
Review 2: approve implementation
State 2: REVIEW_READY -> COMPLETED
```

Допустим один state commit после каждого artifact commit.

Главное требование:

    STATE.md MUST NEVER reference a commit SHA that does not yet exist.

`STATE.md` — runtime metadata, а не implementation artifact: baseline-диффы исключают его (см. exclusion list в `.agents/HARNESS_CONTRACT.md`).

### 12. CI VERIFICATION

После push соответствующего коммита:

1. Определи точный commit SHA.
2. Найди GitHub Actions run, связанный с этим SHA.
3. Убедись, что run существует.
4. Если run ещё выполняется — не объявляй успех.
5. После завершения прочитай conclusion.
6. Проверь, что job `Deterministic Harness` завершился успешно.
7. Зафиксируй `CI_PASSED` только при наблюдаемых доказательствах.
8. Если результат наблюдать нельзя — зафиксируй `CI_UNVERIFIABLE`.
9. Никогда не выводи успех CI из одного факта существования workflow.

Запрещено использовать «latest run» как доказательство: run должен иметь `head_sha == <проверяемый SHA>`; иначе успешный старый run может быть ошибочно приписан новому коммиту.

CI verification state (`CI_NOT_STARTED` / `CI_TRIGGERED` / `CI_RUNNING` / `CI_PASSED` / `CI_FAILED` / `CI_UNVERIFIABLE`) ведётся отдельно от core workflow state machine: CI — внешний enforcement-механизм, а не роль продукта. Эти состояния не добавляются в `.agents/STATE_MACHINE.md`.

### ФИНАЛЬНОЕ ПРАВИЛО

Не считай текст артефакта доказательством сам по себе.

Приоритет источников истины:

1. фактическое состояние файлов репозитория;
2. фактический результат команды или теста;
3. Git history и implementation diff;
4. `PROJECT_SPEC`;
5. `IMPLEMENTATION`;
6. `REVIEW_REPORT`;
7. память агента или предположение.

Если источники противоречат друг другу, более высокий источник имеет приоритет,
а противоречие должно быть явно зафиксировано.

Никогда не превращай отсутствие доказательства в доказательство успеха.
